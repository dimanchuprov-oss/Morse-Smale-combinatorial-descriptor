# Ревью Morse-LiDAR (сентябрь 2026)

Разбор кода на коммите `ee77e4c` (≈2000 строк, 3 коммита) с позиций инженерии,
научной части (ВАК) и акселератора. Колонка «Статус» отражает состояние после
ветки `fix/review-bugs`: ✅ — исправлено, ⚠️ — частично, ❌ — открыто.

## TL;DR

Каркас сделан аккуратно: модули разделены, входные данные проверяются,
программа падает с ошибкой вместо тихого мусора, TTK подключён честно. Но на
момент ревью это ещё не «дескриптор для сравнения объектов». Не хватало трёх
вещей, на которых держится весь питч:

1. **Функции расстояния между дескрипторами.** Без неё не работают поиск
   похожих объектов, классификация и обнаружение изменений. ✅ добавлен
   `morse-lidar-compare` (bottleneck-расстояние между persistence-диаграммами).
2. **Применения порога persistence к дескриптору.** Порог только считался, и на
   реальном шумном лидаре дескриптор тонул в шумовых критических точках.
   ⚠️ Теперь у каждой критической точки есть своя persistence, а порог даёт
   `persistent_counts`. Полной отмены пар в комплексе Морса–Смейла (с
   перестройкой сепаратрис) пока нет.
3. **TTK требует замкнутую поверхность**, а реальный скан почти всегда открытый.
   Поэтому на живых данных работает только эвристический бэкенд. ❌ Открыто.
   Эвристический бэкенд исправлен и стал заметно надёжнее.

## 2. Чего не хватает функционально

- **Сравнения дескрипторов.** ✅ Bottleneck по диаграммам (`morse-lidar-compare`).
  ❌ Нет расстояния на цветном графе (graph edit distance, WL-kernel).
- **Сериализации эвристического дескриптора.** ✅ В JSON теперь попадают
  критические точки (позиция, значение, кратность, persistence) и сепаратрисы.
- **Настоящего упрощения по persistence** (отмена пар с перестройкой
  сепаратрис). ⚠️ Есть persistence каждой точки и `persistent_counts`.
- **Сегментации объекта.** ⚠️ `--remove-plane` удаляет пол или стол через
  RANSAC. Кластеризации объектов нет.
- **Инвариантности к позе.** ⚠️ `--align pca` и `--up-axis`. Настоящего 3D
  (не 2.5D) для эвристического бэкенда по-прежнему нет.
- **Граничного соотношения Морса** для открытых поверхностей. ❌
- **Кривизны на периодической (торовой) сетке.** ❌ Треугольники шва соединяют
  противоположные края, и кривизна там неверна. Пока это сочетание запрещено в CLI.
- **Инженерной части.** ✅ CI (GitHub Actions), тесты на аналитических
  поверхностях, тесты CLI, сквозной пример `examples/synthetic_demo.py`,
  починен тест, который проходил, ничего не проверяя.
  ❌ Нет LICENSE: лицензию выбирает автор, а без неё не обойтись ни на
  акселераторе, ни при публикации кода. ❌ Нет ruff/black и lock-файла.
- **Производительности.** ⚠️ Растеризация, сетки и кривизны векторизованы,
  растр 256×256 целиком обрабатывается за ~3 с. Классификация и трассировка
  пока на Python-циклах, до «миллионов точек» ещё далеко. TTK можно ставить из
  conda-forge (`topologytoolkit`) вместо своей сборки ParaView.

## 3. Научная часть (ВАК)

Постановка правильная. Что стоит добавить:

- **Предшественники.** Раскраска s/u/t (дуальный трёхвалентный граф) очень
  похожа на **трёхцветные графы Ошемкова–Шарко** для классификации потоков
  Морса–Смейла на поверхностях (1998). Стоит проверить и сослаться, это
  усилит работу для ВАК. Близкие работы: Edelsbrunner–Harer–Zomorodian
  (иерархические MSC, 2003), Gyulassy (упрощение MSC).
- **Где научный вопрос.** Для persistence-диаграмм устойчивость доказана:
  bottleneck ≤ ‖f − g‖∞ (Cohen-Steiner, Edelsbrunner, Harer, 2007). А сама
  комбинаторика MSC неустойчива: малый шум меняет граф. Самое интересное —
  найти, при каком пороге и каком скалярном поле комбинаторный граф
  стабилизируется. Это и есть потенциальная новизна.
- **Скалярные поля.** Помимо имеющихся: Heat Kernel Signature, собственные
  функции Лапласа–Бельтрами (вектор Фидлера), геодезическое расстояние. Они
  изометрически инвариантны и менее шумные, чем кривизна.
- **Базовые методы для сравнения:** persistence images/landscapes, ShapeDNA, D2,
  FPFH/SHOT, эмбеддинги PointNet/DGCNN.
- **Датасеты:** ModelNet40/ShapeNet (синтетика), **ScanObjectNN** (реальные
  сканы, ближе всего к задаче), SHREC, TOSCA (деформации).
- **Протокол эксперимента:**
  - шум σ в процентах от диагонали bounding box;
  - разреживание 100% → 5%;
  - случайные повороты из SO(3);
  - три способа реконструкции;
  - четыре и больше скалярных поля;
  - метрики: bottleneck-расстояние, доля совпадений графа, mAP поиска,
    точность классификации.
- **Кривизна и единицы** (баги 2–5) исправлены. До исправления результаты
  экспериментов описывали бы артефакты дискретизации.

### Первые наблюдения после исправлений

- Тор с шумом 0.05: сырые счётчики 69 / 140 / 72 (min / saddle / max), после
  порога persistence 0.5 ровно **1 / 2 / 1**, как у чистого тора. Соотношение
  Эйлера выполняется при любом уровне шума (`tests/test_topology_fixes.py`).
- Синтетические сканы в духе iPhone (`examples/synthetic_demo.py`, высота,
  порог 2 см). Bottleneck-расстояние в размерности 1:
  - повторный скан того же объекта **0.001**;
  - тот же объект с добавленным выступом **0.031** (счётчики показывают лишний
    максимум, изменение найдено);
  - другой объект **0.064**.
- **Кривизна на сыром шумном скане почти целиком состоит из шума.** Даже после
  порога остаются тысячи критических точек. Нужно сглаживание (`--sigma`,
  крупнее `--voxel-size`) или более устойчивые поля (HKS, Лаплас–Бельтрами).
  Это хороший пример для научной части: он показывает, почему выбор скалярного
  поля — центральный вопрос.

## 4. Акселератор

Честное позиционирование: в поиске и классификации нейросетевые эмбеддинги
почти наверняка выиграют. Ниша топологии — **интерпретируемость, работа при
малом количестве данных, обнаружение структурных изменений** (было/стало:
вмятина, трещина, недостающая деталь). Для питча нужны:

- одна конкретная прикладная задача;
- демо «два скана, и вот что изменилось» (`examples/synthetic_demo.py` — его
  прототип на синтетике);
- хотя бы одно сравнение с базовым методом.

## 5. Проверка на iPhone 16 Pro

**Сенсор.** Карта глубины около 256×192, точность порядка 1 см, дальность до
~5 м. Мелкие объекты (кружка, телефон) получатся кашей, нужны объекты от
~30–50 см: стул, рюкзак, колесо, коробка с выступами. ARKit сглаживает и
сливает кадры, так что в файл попадает уже отфильтрованная поверхность. Это
надо оговорить в статье.

**Приложения.** 3d Scanner App (режим LiDAR, экспорт в PLY/XYZ/LAS), SiteScape
(облако точек), Record3D (покадровая глубина, ближе всего к сырым данным).
Polycam и Scaniverse подмешивают фотограмметрию, для научной части это хуже.

**Оси.** В ARKit вертикаль — **Y**, пайплайн считает высотой Z. Для этого
есть `--up-axis y`.

**Протокол съёмки:**

1. 3–4 объекта размером 0,3–1,5 м на пустом полу.
2. Каждый снять 3–5 раз: с разных сторон, с разного расстояния, с разной
   скоростью обхода. Это проверка повторяемости.
3. Для одного объекта пары «до/после»: добавить или убрать деталь. Это главный
   кейс для акселератора.
4. Прогон:

   ```bash
   morse-lidar --input chair1.ply --output chair1.json \
     --up-axis y --remove-plane 0.01 --voxel-size 0.01 \
     --geometry delaunay --persistence-threshold 0.01
   morse-lidar-compare chair1.json chair1_rescan.json
   ```

5. Хороший результат: у повторов одного объекта маленький bottleneck и
   совпадающие `persistent_counts`, у изменённого или другого объекта
   расстояние заметно больше.
